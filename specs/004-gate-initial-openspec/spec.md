# Feature Specification: 从零开始的 OpenSpec 质量门

**Feature Branch**: `004-gate-initial-openspec`

**Created**: 2026-10-26

**Status**: Draft

**Input**: User description: "目前能力针对 OpenSpec 只能做变更审核，不能针对一个从零开始的 OpenSpec 做质量门。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 审核一份从零建立的当前规范 (Priority: P1)

工程师在新项目中写下第一份 OpenSpec。这份规范描述系统应当满足的全部要求，没有更早的已接受规范，也没有一份进行中的增量变更。工程师希望用 SpecGuard 对这份规范和选定版本范围内的代码做质量门审核，而不是先伪造一个变更名称。

报告列出规范中的每条需求、来源位置和证据状态。需求保持原样，不因为“没有旧规范”就被标成新增、修改或删除。选定范围内没有证据的需求标为证据不足。证据不足不是实现错误，也不是需求已经通过。

**Why this priority**: 没有这个能力时，从零建立规范的项目无法使用现有质量门，只能把整份规范塞进一个并不存在的变更里。

**Independent Test**: 准备只有当前规范、没有进行中变更的仓库，并在选定版本范围内放入有证据和无证据的需求。审核不要求变更名称；报告覆盖全部需求，且不把无证据需求写成通过或确定缺陷。

**Acceptance Scenarios**:

1. **Given** 仓库只有从零建立的当前规范，没有进行中的变更，**When** 工程师发起审核，**Then** 系统将该规范作为审核对象，不要求工程师提供变更名称。
2. **Given** 当前规范包含多条需求，**When** 报告生成，**Then** 每条需求保留原始标识和来源位置，且不被标成新增、修改或删除。
3. **Given** 某条需求在选定版本范围内能找到代码或测试证据，**When** 报告生成，**Then** 报告给出证据位置，并区分直接证据与推断关联。
4. **Given** 某条需求在选定版本范围内没有证据，**When** 报告生成，**Then** 该需求标为证据不足，不自动判为实现错误，也不写成已经通过。
5. **Given** 当前规范没有任务清单，**When** 报告生成，**Then** 报告说明任务完整性不可用，不宣称任务已经通过。
6. **Given** 审核结束，**When** 比较审核前后的仓库，**Then** 规范工件、版本索引和提交历史保持不变，报告只写到指定的报告位置。

---

### User Story 2 - 继续审核进行中的变更 (Priority: P1)

已经使用变更审核的工程师升级后，仍按原来的方式审核一份进行中的 OpenSpec 变更。新增、修改、删除语义和任务清单保持原有含义。选择从零建立的当前规范，不会改写这些变更的结论。

**Why this priority**: 新能力如果破坏现有变更审核，正在使用质量门的团队就无法升级。

**Independent Test**: 用现有的单变更和多变更样例各审核一次。需求语义、任务缺口和“未选择时要求明确选择”的行为与增加本功能之前一致。

**Acceptance Scenarios**:

1. **Given** 工程师明确选择一份进行中的变更，**When** 审核开始，**Then** 系统只加载该变更，并保留新增、修改、删除语义。
2. **Given** 仓库只有进行中的变更，没有当前规范，**When** 工程师按原有方式审核，**Then** 审核继续可用，不要求额外字段。
3. **Given** 存在多个进行中的变更且工程师没有选定，**When** 审核开始，**Then** 系统要求明确选择，不擅自挑选。

---

### User Story 3 - 在规范和变更并存时明确选择 (Priority: P2)

一个仓库可能同时有从零建立后仍在使用的当前规范，以及一份或多份进行中的变更。工程师必须能看出本次审核的是整份规范还是某一份变更。系统不能因为两者同时存在就自行决定。

**Why this priority**: 选错对象会把增量变更的结论说成整个系统的结论，或把整份规范的缺口算到一次小变更上。

**Independent Test**: 在同时含有当前规范和两个进行中变更的仓库中，分别验证未选择、选择规范、选择其中一个变更。未选择时在检查开始前停止；选择后的报告对象与选择一致。

**Acceptance Scenarios**:

1. **Given** 当前规范和至少一个进行中的变更同时存在，且工程师没有选定对象，**When** 审核开始，**Then** 系统在任何检查开始前停止，并说明需要选择整份规范或哪一份变更。
2. **Given** 工程师选择当前规范，**When** 审核开始，**Then** 进行中的变更不被当作本次需求来源。
3. **Given** 工程师选择其中一个变更，**When** 审核开始，**Then** 当前规范中的其他需求不被算作该变更的需求。
4. **Given** 同一轮审核同时指定了互相冲突的规范对象和变更对象，**When** 校验选择，**Then** 系统在检查开始前拒绝，并指出冲突。

---

### User Story 4 - 在报告中区分审核对象 (Priority: P2)

阅读报告的人需要知道结论来自整份当前规范，还是来自一份进行中的变更。两种报告都列出找到和缺失的工件，并且需求统计与对象实际内容一致。

**Why this priority**: 对象不清楚时，工程师无法判断证据不足是整份规范的缺口，还是一次变更的缺口。

**Independent Test**: 分别审核当前规范和一份变更。两份报告都能看出对象种类和对象名称；当前规范的报告不出现该变更才有的增量语义。

**Acceptance Scenarios**:

1. **Given** 审核对象是当前规范，**When** 报告生成，**Then** 报告标明对象为当前规范，并列出找到和缺失的工件。
2. **Given** 审核对象是进行中的变更，**When** 报告生成，**Then** 报告标明对象为该变更，而不是整份当前规范。
3. **Given** 当前规范的某份工件缺失，**When** 报告生成，**Then** 缺失按当前规范的工件说明，不把变更专有工件说成当前规范必须具备。

---

### Edge Cases

- 当前规范存在，但其中没有任何可审核的需求。系统说明基于需求的审核不可用，不宣称需求符合性已经通过。
- 当前规范中的需求标识重复、正文为空，或工件无法读取。系统在检查开始前停止，并给出可操作的错误。
- 当前规范由多组能力组成。全部需求都进入同一次审核，每条需求保留所属能力和来源位置。
- 选定版本范围为空，或范围内没有代码和测试。所有需求标为证据不足，审核仍完成并说明范围内没有可核验证据。
- 版本范围之外的已有代码，不得被当作本次需求已经实现的证据。
- 工程师把第一份规范放在进行中的变更里，而不是当前规范中。该情况继续按变更审核处理，不在本功能中改写。
- 仓库既没有当前规范，也没有进行中的变更。系统说明基于需求的审核不可用。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须把从零建立的当前 OpenSpec 作为一种审核对象，与进行中的变更审核并存。
- **FR-002**: 当前规范中的需求必须按原标识和来源位置进入审核，不得仅因不存在更早规范而标成新增、修改或删除。
- **FR-003**: 只有当前规范、没有进行中变更时，工程师必须能在不提供变更名称的情况下开始审核。
- **FR-004**: 当前规范与进行中变更同时存在且未做选择时，系统必须在任何检查开始前停止，并要求选择其中一种对象。
- **FR-005**: 同一轮审核不得同时使用互相冲突的当前规范和变更作为需求来源；冲突必须在检查开始前拒绝。
- **FR-006**: 工程师明确选择进行中的变更时，系统必须保持原有变更加载、增量语义、任务审核和未选择时的行为。
- **FR-007**: 需求证据必须来自工程师选定的版本范围。范围内没有证据的需求必须标为证据不足。
- **FR-008**: 版本范围之外的文件不得作为需求已经实现的证据。
- **FR-009**: 证据不足不得被写成确定的实现错误，也不得被写成需求已经通过。
- **FR-010**: 当前规范没有可审核需求时，系统必须说明基于需求的审核不可用，不得宣称需求符合性已经通过。
- **FR-011**: 当前规范没有任务清单时，系统必须说明任务完整性不可用，不得宣称任务已经通过。
- **FR-012**: 报告必须标明审核对象是当前规范还是进行中的变更，并列出找到和缺失的工件。
- **FR-013**: 当前规范由多组能力组成时，全部需求必须纳入同一次审核，并保留各自的能力名称和来源位置。
- **FR-014**: 无法读取、需求标识重复或需求正文为空时，系统必须在检查开始前停止，并说明原因。
- **FR-015**: 审核不得修改规范工件、版本索引或提交历史；报告只写到指定的报告位置。
- **FR-016**: 第一份规范若放在进行中的变更中，系统必须继续按变更审核，不得静默改成当前规范审核。
- **FR-017**: 已有的 Spec Kit 功能审核和只含旧变更配置的审核必须继续可用。

### Key Entities

- **当前规范**: 从零建立、描述系统全部要求的 OpenSpec。它不是一份进行中的增量变更。
- **进行中的变更**: 在当前规范之外单独提出的增量变更，保留新增、修改、删除语义和任务清单。
- **审核对象**: 一次审核所针对的当前规范或进行中的变更，包含对象种类和对象名称。
- **需求**: 当前规范或变更中的一条要求，保留标识、正文、所属能力和来源位置。
- **版本范围**: 工程师选定的、用于寻找实现证据的代码范围。范围之外的文件不构成证据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在标准的从零规范样例中，100% 的需求以原始标识和来源位置出现，被标成新增、修改或删除的数量为 0。
- **SC-002**: 只有当前规范时，工程师不提供变更名称也能完成审核；报告包含全部需求。
- **SC-003**: 现有变更审核样例在增加本功能后保持通过，增量语义和未选择时的行为不变。
- **SC-004**: 当前规范与变更并存且未选择时，100% 的此类审核在检查开始前停止。
- **SC-005**: 选定范围内没有证据的需求，100% 标为证据不足，其中 0% 被写成已通过或确定缺陷。
- **SC-006**: 审核前后，规范工件、版本索引和提交历史保持不变。

## Assumptions

- “从零开始的 OpenSpec”指项目当前已接受的整份需求规范，不是进行中变更里的增量。
- 代码证据仍限定在工程师选定的版本范围内。本功能不把仓库里范围之外的历史代码自动算作已实现。
- 本功能不评估规范的文笔，也不生成、补全或归档规范。
- 本功能不接受、不拒绝、也不合并变更。是否接受仍由工程师决定。
- 已交付的变更审核和 Spec Kit 审核保持原行为。本功能是在二者之外增加的一种 OpenSpec 审核对象。
- 第一份规范如果仍然放在进行中的变更里，继续使用现有变更审核，不属于本功能要改写的场景。
