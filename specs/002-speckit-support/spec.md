# Feature Specification: SpecGuard 支持 Spec Kit 需求来源

**Feature Branch**: `002-speckit-support`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "创建新分支，让 SpecGuard 支持 Spec Kit。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 审核一个 Spec Kit 功能 (Priority: P1)

工程师的 Java 仓库用 Spec Kit 管理需求和任务，而不是 OpenSpec。仓库里有一个 `specs/<编号-名称>/` 功能目录，其中有规格和任务清单。工程师发起一次审核后，报告要能回答需求符合性、任务完整性、代码风险、测试有效性和审核效率，并为结论附上证据或标成证据不足。

**Why this priority**: 没有这条路径，Spec Kit 仓库无法得到 SpecGuard 的质量报告。

**Independent Test**: 对一个只有一个 Spec Kit 功能的 Java 样例仓库运行审核。报告列出该功能的规格条目和任务，并且不修改规格、任务、源文件和 Git 历史。

**Acceptance Scenarios**:

1. **Given** 仓库只有一个含规格文件的 Spec Kit 功能目录，并且基线可以解析，**When** 工程师发起审核，**Then** 系统选中该功能，报告写明功能名、找到的规格和任务、缺失的工件，以及实际基线和目标。
2. **Given** 审核正常结束，**When** 比较审核前后的仓库，**Then** 业务源文件、规格、任务和提交历史不变，报告只出现在指定的报告目录。
3. **Given** 工程师查看报告，**When** 阅读结论，**Then** 报告仍包含需要人工审核、需求覆盖、潜在风险、证据定位和限制说明。缺少证据不会被写成代码一定有错，没有发现也不会被写成代码安全。

---

### User Story 2 - 已勾选任务必须有支撑 (Priority: P1)

Spec Kit 任务清单里标成完成的任务，应当能在本次变更的代码或测试里找到支撑。没有支撑时，工程师要看到任务完整性缺口，而不是一句“代码有错”。

**Why this priority**: 任务被勾完但没有实现，是 Spec Kit 流程里最需要质量门核对的情况。

**Independent Test**: 准备一条规格标识能在变更文件中找到的需求，一条找不到标识的需求，以及一条已勾选但变更里没有对应代码或测试的任务。报告按证据级别和任务缺口标注。

**Acceptance Scenarios**:

1. **Given** 变更文件内容包含某条需求标识，**When** 报告生成，**Then** 该需求的证据为直接证据，并给出文件位置。
2. **Given** 只有文件名重叠、正文没有需求标识，**When** 报告生成，**Then** 证据至多为推断，不能单独当成需求已实现。
3. **Given** 任务清单将该任务标成完成，且变更中没有代码或测试支撑，**When** 报告生成，**Then** 该任务出现在任务完整性缺口中，并且不因此断言代码一定有错。

---

### User Story 3 - 不悄悄改掉 OpenSpec，也不自动挑一个功能 (Priority: P1)

已有 OpenSpec 仓库的审核行为保持不变。一个仓库如果同时有 OpenSpec 变更和 Spec Kit 功能，或者有多个 Spec Kit 功能，工程师必须明确选择。系统不得擅自挑选。

**Why this priority**: 自动挑选会把报告安到错误的需求上，并可能破坏已经交付的 OpenSpec 审核。

**Independent Test**: 分别运行只有 OpenSpec 的样例、有两个 Spec Kit 功能且未选择的样例，以及两种需求来源同时存在且未选择的样例。

**Acceptance Scenarios**:

1. **Given** 仓库只有 OpenSpec 变更，**When** 工程师按现有方式审核，**Then** 所选变更、证据规则和报告章节与支持 Spec Kit 之前一致。
2. **Given** 存在多个 Spec Kit 功能且工程师没有指定功能，**When** 审核开始，**Then** 系统在执行检查前停止，列出功能名，不生成报告，也不自动采用 `.specify/feature.json` 里的当前功能。
3. **Given** OpenSpec 与 Spec Kit 同时存在且工程师没有指定来源，**When** 审核开始，**Then** 系统在执行检查前停止，并列出两种来源，不自动挑一种。

---

### User Story 4 - 超出范围时说明不支持 (Priority: P2)

仓库使用 Spec Kit，但不是 Java 服务端项目，或者找不到规格。工程师应看到明确限制，而不是一份看起来已经覆盖代码风险和测试的通过报告。

**Why this priority**: 认错项目类型比拒绝审核更危险。

**Independent Test**: 对一个非 Java 的 Spec Kit 仓库，以及一个没有规格文件的功能目录运行审核。

**Acceptance Scenarios**:

1. **Given** 仓库能认出 Spec Kit 布局但不是 Java 服务端项目，**When** 审核结束，**Then** 报告说明代码检查和构建检查不支持该项目，并且不宣称需求符合性或代码风险已经通过。
2. **Given** 所选功能没有规格文件，**When** 审核开始，**Then** 报告说明基于需求的审核不可用，不把缺失写成需求已满足。

---

### Edge Cases

- 功能目录名称不符合「编号-名称」或目录里没有规格文件时，不把它算作可选功能。
- 任务清单缺失时，报告标明任务工件缺失，不把任何任务当成已完成。
- 规格里没有可识别的需求条目时，需求符合性标为不可用，不编造需求标识。
- 被审核仓库自己的原则文件只作为限制说明引用，不改写 SpecGuard 的审核策略，也不向外发送。
- 工程师指定了不存在的功能名时，审核在检查前停止并指出该名称，不改用另一个功能。
- SpecGuard 不执行 Spec Kit 的规格、计划、任务或实现命令，也不替仓库勾选任务或修改规格。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在仓库的 `specs/` 下发现符合「编号-名称」且含有规格文件的功能目录。
- **FR-002**: 只有一个这样的功能时，系统必须选中它。多于一个且未明确指定时，系统必须在检查前停止并列出名称，不得自动挑选，也不得仅凭 `.specify/feature.json` 挑选。
- **FR-003**: 系统必须解析所选功能的规格，识别用户故事、验收场景和功能需求标识，并报告哪些工件存在、哪些缺失。
- **FR-004**: 系统必须解析所选功能的任务清单。标成完成但没有代码或测试支撑的任务必须标成任务完整性缺口，不得因此断言代码一定有错。
- **FR-005**: 需求与变更代码的关联必须区分直接证据、推断和证据不足。只有变更文件内容包含需求标识才算直接证据。仅有文件名重叠不得当作需求已实现。
- **FR-006**: 找不到规格或需求条目不足以核验时，系统必须说明基于需求的审核不可用，不得宣称需求符合性已经通过。
- **FR-007**: 只有 OpenSpec 的仓库必须保持现有审核行为，包括变更选择、证据级别和只读边界。
- **FR-008**: OpenSpec 与 Spec Kit 同时存在且未指定来源时，系统必须在检查前停止并列出两种来源，不得自动挑一种。
- **FR-009**: 非 Java 服务端项目必须被说明为代码检查不支持，不得假装构建、测试或代码风险已经被覆盖。
- **FR-010**: 审核不得修改业务源文件、规格、任务、版本索引或提交历史，不得执行 Spec Kit 命令，不得自动提交、合并或勾选任务。
- **FR-011**: 被审核仓库的原则文本只能写入限制说明。它不得改写审核策略，也不得被发送到外部服务。
- **FR-012**: 报告必须继续回答五个质量问题，并保留“缺少测试证据不等于代码有错、检查未发现问题不等于代码安全”的说明。

### Key Entities

- **需求来源**: OpenSpec 或 Spec Kit。一次审核只使用一个来源。
- **Spec Kit 功能**: 一个带编号的功能目录，包含规格和可选的任务清单。
- **规格条目**: 用户故事、验收场景或带标识的功能需求，能被证据关联。
- **任务项**: 任务清单中的一条，带有是否标成完成的状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对一个只有单个 Spec Kit 功能的受支持 Java 变更，一次审核后的报告同时回答五个质量问题。抽查时，每条结论要么有可核查证据，要么标为证据不足。
- **SC-002**: 在准备好的样例中，缺少实现证据的需求条目和已勾选但没有支撑的任务都被标成缺口。仅因缺少证据而被写成“代码一定有错”的条目为 0。
- **SC-003**: 存在多个 Spec Kit 功能且未指定时，命令在检查前停止，输出包含全部功能名，报告文件数量为 0。
- **SC-004**: 既有 OpenSpec 样例的审核结果与增加 Spec Kit 支持之前一致。
- **SC-005**: 非 Java 的 Spec Kit 样例不会得到“代码风险和测试已经通过”的结论。

## Assumptions

- 本功能只增加 Spec Kit 这一种需求来源。代码检查仍然只覆盖 Java 服务端仓库。
- 功能目录沿用 Spec Kit 的 `specs/<编号-名称>/` 布局。规格文件和任务清单使用 Spec Kit 现有的用户故事、功能需求标识和勾选任务写法。
- 被审核仓库不需要安装 Spec Kit 命令。SpecGuard 只读取文件。
- 默认策略仍是建议模式。本功能不新增合并门禁，也不把模型假设变成阻断条件。
- 宪章当前要求需求由 OpenSpec 管理。在宪章把 Spec Kit 写成允许的需求来源之前，本功能不得实现。
