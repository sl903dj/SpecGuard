# Feature Specification: SpecGuard 变更质量守卫

**Feature Branch**: `001-specguard-quality-gate`

**Created**: 2026-10-16

**Status**: Draft

**Input**: User description: "项目代号 SpecGuard，意思是 AI 编程流程中的规范与质量守卫。产品定位是 AI Coding Quality Gate，而不是另一个 AI Coding Agent。它应自动回答需求符合性、任务完整性、代码风险、测试有效性和审核效率五个问题，并为每个结论提供可核查的证据。核心产物是从需求到代码、从代码到测试的变更质量报告，可在本地生成，也可进入拉取请求；工程师仍决定是否接受变更。完整规格来源为 SpecGuard v0.1 OpenSpec 包。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 获得一份可核查的变更质量报告 (Priority: P1)

使用 AI 编程助手的工程师完成一次代码变更后，希望知道这次变更能不能交给人工审核，以及审核时应该先看哪里。工程师对选定的需求变更发起一次审核，得到一份变更质量报告。报告回答五个问题：需求是否都有实现、已完成任务是否真有代码或测试支撑、是否引入明显风险、测试是否真的验证了需求、哪些地方要优先看。每条结论都附带可核查的证据，或明确标成证据不足。

报告同时说明哪些检查已经有可靠证据、不必反复人工确认。它区分“需要人工审核”和“已有可靠证据”。缺少测试证据不会被写成“代码一定有错”；已有检查未发现问题也不会被写成“代码安全”。

工程师可以在本地阅读这份报告，也可以把它放进拉取请求。SpecGuard 不代替工程师接受或拒绝变更。

**Why this priority**: 没有这份报告，产品就没有可交付的价值。其他能力都是为了让报告诚实、可追溯、可复核。

**Independent Test**: 对一个准备好的变更运行一次审核。只检查报告是否包含人工审核提示、需求覆盖、潜在风险、证据定位和限制说明，并且仓库中的业务文件、需求工件和版本历史都没有被改动。

**Acceptance Scenarios**:

1. **Given** 当前目录位于一个有效的版本库中，且基线版本可以解析，**When** 工程师发起审核，**Then** 系统识别版本库根目录，报告实际采用的基线版本和目标版本，并生成人类可读报告和结构化报告。
2. **Given** 所有必需检查都已结束，**When** 工程师阅读报告，**Then** 报告汇总每项检查的结果、发现、证据缺口，以及本次审核的版本、所选变更、配置版本和所用工具版本。
3. **Given** 本次没有产生任何发现，**When** 工程师阅读报告，**Then** 报告写明实际执行了哪些检查，并且不宣称代码没有缺陷。
4. **Given** 某项必需检查失败、超时或未能执行，**When** 报告生成，**Then** 报告标出缺失的证据，并且不得把本次审核呈现为干净通过。
5. **Given** 审核正常结束，**When** 比较审核前后的仓库，**Then** 业务源文件、需求工件、版本索引和提交历史保持不变；报告只写到指定的报告位置，不覆盖源文件。
6. **Given** 工程师把报告交给同事，**When** 同事查看结论，**Then** 同事能看到“需要人工审核”、需求覆盖、潜在风险和证据定位，并能沿着证据找到相关需求条目、变更文件、代码位置、测试结果和检查规则。
7. **Given** 工程师请求查看用法说明或产品版本，**When** 系统响应，**Then** 系统只提供对应信息，不启动审核。

### User Story 2 - 核对需求符合性与任务完整性 (Priority: P1)

审核工程师需要确认：需求里要求的功能是否都有实现，有没有遗漏，有没有与需求对不上的擅自扩展；OpenSpec 里标成完成的任务，是否真有对应代码或测试支撑。

SpecGuard 读取所选变更中的需求、方案说明、任务和相关长期规范，并把它们与变更代码、测试证据关联起来。文件刚好被改过，不足以单独证明某条需求已经实现。直接证据、推断关联和证据不足必须分开。证据不足只表示还不能下结论，不自动等于实现错误。

**Why this priority**: 五个问题里，需求遗漏和“任务已勾完但没有实质支撑”是人工审核最容易漏掉、也最耗费时间的部分。

**Independent Test**: 准备一组变更，其中分别包含有实现证据的需求、没有证据的需求、表述含糊的需求、被修改或删除的需求，以及标成完成但没有代码或测试支撑的任务。报告必须按各自情况标注，且不把证据不足写成确定缺陷。

**Acceptance Scenarios**:

1. **Given** 工程师明确指定了一个需求变更，**When** 审核开始，**Then** 系统加载该变更的相关工件，并报告哪些工件找到了、哪些缺失。
2. **Given** 一条需求能关联到代码和测试证据，**When** 报告生成，**Then** 报告给出该需求的标识和证据位置，并区分直接证据与推断关联。
3. **Given** 一条需求找不到证据，**When** 报告生成，**Then** 该需求被标为证据不足，且不被自动判定为实现错误。
4. **Given** 一条需求信息不足以可靠核验，**When** 报告生成，**Then** 该需求被标为需要人工审核，并说明缺少或含糊的信息是什么。
5. **Given** 所选变更包含被修改或被删除的需求，**When** 审核进行，**Then** 系统把这种变更语义纳入审核上下文，且不把每一项被删除的行为都当成实现缺陷。
6. **Given** 某项任务在变更任务清单中被标为完成，**When** 找不到对应的代码或测试支撑，**Then** 报告把它标成任务完整性缺口，且不因此断言代码一定有错。
7. **Given** 变更中出现无法追溯到任何需求的行为，**When** 报告生成，**Then** 报告把它标为可能的擅自扩展，并要求人工审核，而不是直接判为缺陷。
8. **Given** 存在多个进行中的变更且工程师没有选定，**When** 审核开始，**Then** 系统要求明确选择，或遵循已经明确配置的选择策略，不擅自挑选一个变更。
9. **Given** 找不到需求规范所在位置，**When** 审核继续，**Then** 系统说明基于需求的审核不可用，并且不宣称需求符合性已经通过。

### User Story 3 - 在没有辅助审查时完成基础质量检查 (Priority: P1)

工程师有时不能或不打算使用辅助审查。此时 SpecGuard 仍要完成已配置的确定性检查，例如项目原有的构建和测试，并如实记录结果。检查未执行、工具缺失或超时，都不能被记成通过。

**Why this priority**: 基础检查不依赖辅助审查，是报告里最可靠的一类证据，也是审核效率的前提。

**Independent Test**: 在不配置辅助审查的情况下运行审核。构建成功、构建失败、工具缺失和检查超时四种情况，都必须得到互不相同且符合定义的结果；辅助审查相关维度全部标为未执行。

**Acceptance Scenarios**:

1. **Given** 已配置的构建命令成功结束，**When** 检查完成，**Then** 该项标为通过，并记录实际执行的命令、耗时和结束状态。
2. **Given** 已配置的构建命令失败，**When** 检查完成，**Then** 该项标为失败，并保留有限度的诊断摘要。
3. **Given** 已配置的检查工具不存在，**When** 检查结束，**Then** 该项按配置标为跳过或错误，且绝不标为通过。
4. **Given** 某项检查超过规定时限，**When** 时限到达，**Then** 该项标为超时，系统尽量终止它所管理的进程，并保留诊断摘要。
5. **Given** 没有配置辅助审查，**When** 审核结束，**Then** 确定性检查仍然可用，报告把所有辅助审查维度标为未执行。
6. **Given** 仓库包含多个构建模块，**When** 审核识别项目，**Then** 报告列出识别到的模块，并按已配置的范围处理，不静默漏掉受影响的模块。
7. **Given** 项目布局无法可靠识别，**When** 审核继续，**Then** 系统说明这一限制；在允许的前提下，仍可执行工程师明确配置的命令。
8. **Given** 配置无效，**When** 工程师发起审核，**Then** 系统在执行任何检查之前停止，并指出无效的设置。

### User Story 4 - 标出代码风险并安排审核顺序 (Priority: P2)

高级工程师没有时间通读 AI 生成的全部改动。报告需要指出明显的边界条件、异常处理、兼容性和潜在回归，并说明应先看哪里。已有可靠证据的检查不必反复人工确认。

每一条风险都要指向具体位置，并给出一条说得通的出错路径。不能确认的判断必须标成待复核的假设。不同检查得出矛盾结论时，矛盾要保留，不能被收成一个干净结果。

**Why this priority**: 这直接降低人工审核的机械工作，但必须建立在报告和证据规则已经可靠的基础上。

**Independent Test**: 使用含有已知边界问题、异常处理问题和公开接口变化的样例变更。报告应指出位置和可能的失败路径，把最高风险放在前面，并区分已证实的工具发现与待复核假设。

**Acceptance Scenarios**:

1. **Given** 变更后的代码路径看起来错误处理了边界条件，**When** 形成发现，**Then** 发现指出相关代码位置，描述一种说得通的输入或执行路径，并区分“疑似缺陷”和“已由工具证实的发现”。
2. **Given** 变更后的代码可能吞掉、误判或错误传递异常，**When** 形成发现，**Then** 系统给出相关证据和理由，并且在没有说得通的失败场景时不宣称存在缺陷。
3. **Given** 变更影响事务边界、共享状态或并发执行，**When** 审核进行，**Then** 系统检查手头可用的相关上下文；所需上下文不可用时，报告写明限制。
4. **Given** 可靠判断需要缺失的代码、配置或领域规则，**When** 审核进行，**Then** 系统报告证据不足，并且不编造缺失的实现细节。
5. **Given** 变更的公开接口可能影响既有调用方，**When** 审核进行，**Then** 系统给出能够找到的调用方或约定证据，并报告潜在的兼容性风险。
6. **Given** 变更影响数据保存、数据结构或已持久化的数据，**When** 审核进行，**Then** 系统报告相关的迁移和兼容性关注点，并区分已核实的不兼容与假设。
7. **Given** 依赖、构建配置或应用配置发生变化，**When** 审核进行，**Then** 系统审查现有变更信息，并报告相关的版本、兼容性或配置风险。
8. **Given** 审核期间某个既有测试失败，**When** 报告生成，**Then** 报告包含这次失败；除非证据支持，否则不宣称就是当前变更导致的。
9. **Given** 报告中同时存在高风险项和已有可靠证据的检查，**When** 工程师打开报告摘要，**Then** 最高风险项排在应优先查看的位置，已有可靠证据的项被标为不必反复人工确认。
10. **Given** 多个检查报告了同一个底层问题，**When** 报告生成，**Then** 系统应把很可能重复的发现归在一起，并保留各自的原始证据和来源。
11. **Given** 不同检查得出相互冲突的结论，**When** 报告生成，**Then** 系统保留冲突，不把分歧悄悄收成一个干净结论。

### User Story 5 - 判断测试是否真正验证了需求 (Priority: P2)

测试通过并不等于需求已经满足。工程师需要知道：测试有没有覆盖变更后的行为，有没有覆盖关键边界、失败路径和异常路径，断言有没有真正检查预期行为，还是只做了几个简单判断。

**Why this priority**: 测试有效性是五个核心问题之一。它依赖需求追溯和测试执行结果，因此排在这两项之后。

**Independent Test**: 准备三类样例：测试通过但未覆盖关键边界、测试失败、测试命令本身执行出错。报告必须区分这三类，并且在没有覆盖率数据时不编造覆盖率数字。

**Acceptance Scenarios**:

1. **Given** 已配置的测试命令成功，**When** 报告生成，**Then** 报告记录通过结果，并且不据此推断所有业务需求都已满足。
2. **Given** 已配置的测试命令失败，**When** 报告生成，**Then** 报告保留失败状态和诊断证据，并区分“测试发现失败”和“测试未能执行”。
3. **Given** 某个重要的边界、反向场景或异常场景找不到测试证据，**When** 报告生成，**Then** 系统报告测试覆盖关注点，并说明它对应的需求或变更后的代码路径。
4. **Given** 与某条需求相关的测试只包含不能验证该需求的简单断言，**When** 报告生成，**Then** 系统把这标成测试有效性不足，并指向相关测试和需求。
5. **Given** 无法产生覆盖率数据，**When** 报告生成，**Then** 覆盖率分析被标为不可用，且不编造覆盖率百分比。

### User Story 6 - 在内网使用辅助审查且不外泄材料 (Priority: P2)

团队可以启用辅助审查，让内部模型帮助查看需求符合性、业务逻辑、测试有效性和回归风险。模型输出在得到可核验证据支持之前，只是待复核假设。源码、需求文档和日志默认留在内部。未配置内部审查服务时，系统不联系外部模型服务。

**Why this priority**: 辅助审查能发现确定性检查难以判断的问题，但它不可靠，也不能突破数据保护边界。因此它是增强能力，不是报告成立的前提。

**Independent Test**: 分别在“未配置审查服务”“服务不可达”“返回内容无法解析”“源码中夹带试图指挥审核者的文字”四种情况下运行。材料不得被改送到其他服务，其他已成功的检查必须保留。

**Acceptance Scenarios**:

1. **Given** 工程师启用了已明确配置的内部审查服务，**When** 辅助审查运行，**Then** 系统只发送该审核任务所需的上下文，并在可得时记录服务标识和模型标识。
2. **Given** 已配置的审查服务无法连接，**When** 辅助审查失败，**Then** 系统报告这一错误，并且不把源码悄悄发给另一个服务。
3. **Given** 审查服务返回无效或不完整的结构化结果，**When** 处理该结果，**Then** 受影响的审查标为错误，其他已经成功的检查仍然保留。
4. **Given** 源码、注释、文档或测试数据中含有针对审核者的指示，**When** 审核进行，**Then** 这些文字只被当作不可信的源内容，不能改写审核策略。
5. **Given** 准备送去辅助审查的内容里发现疑似密钥，**When** 系统处理该内容，**Then** 系统按策略遮盖或排除密钥，并报告发生过遮盖，且不把密钥本身写出来。
6. **Given** 报告写出，**When** 工程师查看报告，**Then** 报告不包含环境密钥、访问令牌，也不包含不必要的源码摘录。
7. **Given** 辅助审查提出一条没有确定性检查支撑的假设，**When** 应用审核策略，**Then** 该假设默认不阻止合并。

### User Story 7 - 按策略给出建议或阻断信号 (Priority: P3)

技术负责人希望先以建议方式试用，等真实历史变更上的误报和漏报可以被接受后，再考虑用确定性失败阻止合并。模型自己的判断不能单独阻止合并。必需检查被跳过时，严格策略不能把它算作成功。

**Why this priority**: 阻断会直接影响合并。在报告质量和真实评估完成之前，它不应成为默认行为。

**Independent Test**: 用同一组发现分别套用建议策略和严格策略。建议策略只报告、不阻止；只有配置所指定的确定性失败才产生阻断；被跳过的必需检查在严格策略下不算通过。

**Acceptance Scenarios**:

1. **Given** 选择了建议策略，**When** 审核产生发现，**Then** 发现被写入报告，且不自动阻止合并。
2. **Given** 已配置的阻断规则发现了符合条件的确定性失败，**When** 策略计算结束，**Then** 结果为策略阻断。
3. **Given** 某项必需检查被跳过、不可用或未完成，**When** 使用严格策略，**Then** 该检查不算成功。
4. **Given** 尚未用真实历史变更完成误报与漏报对照，**When** 团队使用 v0.1，**Then** 产品保持建议模式，不启用会阻止合并的质量门禁。

---

### Edge Cases

- 当前目录不在版本库中时，系统在执行检查前停止，并给出可操作的错误说明。
- 指定的基线版本无法解析时，系统报告错误，不用另一个版本悄悄代替。
- 工程师明确要求包含未提交的改动时，报告区分已提交变更和未提交变更；未明确要求时，不把工作区改动混入审核。
- 审核进行期间被审核的源状态发生变化时，系统在能够发现的情况下指出不一致；证据不再对应当时审核的状态时，报告标为不完整。
- 变更文件被重命名或删除时，报告仍能说明变更类型和受影响范围。
- 发现无法对应到精确的代码位置时，位置标为不可用，或给出更宽的证据引用，不编造行号。
- 构建工具可能生成文件或执行项目自带脚本时，系统说明这一风险；对不可信仓库，支持在隔离的工作区中执行。
- 需求文档不完整或自相矛盾时，相关条目进入人工审核，不靠猜测补全需求。
- 辅助审查的上下文装不下整个仓库时，系统只使用与本次变更有关的有限上下文，并说明因此带来的限制。
- 目标项目依赖内部构件库或特殊环境、导致构建无法执行时，该项标为失败、错误或超时中的实际结果，不标为通过。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在开始审核前识别版本库根目录；当前目录不在版本库中时，必须在执行检查前停止，并给出可操作的错误说明。
- **FR-002**: 系统必须解析已配置或明确指定的基线版本与目标版本，并在报告中写明实际采用的版本；基线无法解析时必须报错，不得悄悄替换。
- **FR-003**: 系统必须从版本历史中识别变更文件和变更行范围，并在可得时区分新增、修改、删除和重命名。
- **FR-004**: 只有工程师明确启用时，系统才把未提交的工作区或暂存变更纳入审核，并且必须把它们与已提交变更区分开。
- **FR-005**: 审核期间被审核的源状态发生变化时，系统必须在能够发现时指出不一致；证据不再对应所审核状态时，报告必须标为不完整。
- **FR-006**: 系统必须在不修改需求工件的前提下，发现并解析所选变更的提案、设计、任务、增量需求和相关长期规范，并报告哪些工件存在、哪些缺失。
- **FR-007**: 存在多个进行中的变更且未做选择时，系统必须要求明确选择，或遵循已明确配置的选择策略，不得擅自挑选。
- **FR-008**: 找不到需求规范位置时，系统必须说明基于需求的审核不可用，并且不得宣称需求符合性已经通过。
- **FR-009**: 系统必须把需求与变更代码、测试证据关联起来，并区分直接证据、推断关联和证据不足。仅有文件重叠不得当作需求已经实现的充分证据。
- **FR-010**: 找不到需求证据时，系统必须将该需求标为证据不足，不得自动判定实现错误。
- **FR-011**: 需求信息不足以可靠核验时，系统必须将其标为需要人工审核，并说明缺少或含糊的信息。
- **FR-012**: 所选变更包含被修改或被删除的需求时，系统必须把该变更语义纳入审核，且不得把每一项被删除的行为都当成实现缺陷。
- **FR-013**: 系统必须检查任务清单中标为完成的任务是否有对应代码或测试支撑；没有支撑时必须标成任务完整性缺口，且不得因此断言代码一定有错。
- **FR-014**: 系统必须标出无法追溯到需求的变更行为，并将其作为可能的擅自扩展交给人工审核，而不是直接判为缺陷。
- **FR-015**: 系统必须独立于辅助审查执行已配置的确定性检查。每项检查的结果只能是通过、失败、跳过、错误或超时之一。
- **FR-016**: 检查通过时，系统必须记录实际执行的命令、耗时和结束状态。检查失败、超时或执行出错时，必须保留有限度的诊断摘要。
- **FR-017**: 已配置的工具不存在时，该检查必须标为跳过或错误，不得标为通过。超过时限时必须标为超时，并尽量终止系统所管理的进程。
- **FR-018**: 未配置辅助审查时，确定性检查必须仍然可用，且所有辅助审查维度必须标为未执行。
- **FR-019**: 系统必须识别受支持项目的构建配置，只执行已配置且被允许的构建与测试命令，并报告识别到的构建模块。不得静默漏掉受影响的模块。
- **FR-020**: 项目布局无法可靠识别时，系统必须说明限制；在允许的前提下，可以执行工程师明确配置的命令。
- **FR-021**: 系统必须支持对变更后业务逻辑的证据化审核，覆盖边界条件、异常处理、状态流转、空值与空输入、事务边界、并发和相关的授权检查。每条此类发现必须指出代码位置，并给出说得通的失败路径。
- **FR-022**: 系统必须区分疑似缺陷与已由工具证实的发现。没有说得通的失败场景，或缺少必要上下文时，必须报告证据不足，不得编造实现细节或行号。
- **FR-023**: 系统必须评估与变更行为相关的测试证据，包括测试执行结果、关联测试、边界与反向场景、异常路径，以及不能验证目标行为的简单断言。
- **FR-024**: 测试通过时，系统必须记录通过结果，且不得推断所有需求均已满足。测试失败必须与测试未能执行区分开。
- **FR-025**: 重要边界、反向场景或异常场景缺少测试证据时，系统必须报告测试覆盖关注点，并说明对应的需求或代码路径。无法获得覆盖率数据时，不得编造覆盖率百分比。
- **FR-026**: 系统必须评估变更对既有行为的潜在影响，包括公开接口、调用方、数据保存与数据约定、依赖和配置。必须区分已核实的不兼容与假设。
- **FR-027**: 审核期间既有测试失败时，报告必须包含该失败；除非证据支持，不得宣称是当前变更导致的。
- **FR-028**: 系统必须把确定性检查和辅助审查的发现归一为同一类审核发现。每条发现必须包含报告内稳定的标识、类别、严重程度、摘要、证据状态和来源；有位置时必须包含文件和行信息。
- **FR-029**: 系统应把很可能重复的发现归在一起，并保留原始证据和来源标识。相互冲突的结论必须保留，不得收成一个干净结果。
- **FR-030**: 系统必须同时生成人类可读报告和结构化报告。两者都包含检查结果、发现、证据缺口、限制说明和执行信息。结构化报告的结构在同一产品版本内保持稳定。
- **FR-031**: 报告必须包含需要人工审核的提示、需求覆盖、潜在风险和证据定位。证据定位必须能关联到需求条目、变更文件、代码位置、测试结果和检查规则中实际可得的那些项。
- **FR-032**: 报告必须写明：缺少测试证据不等于代码一定有错；静态或自动检查未发现问题也不等于代码安全。没有任何发现时，必须写明实际执行了哪些检查，不得宣称代码没有缺陷。
- **FR-033**: 必需检查未能执行或超时时，报告必须标出缺失证据，不得把审核呈现为干净通过。审核的整体结果必须区分审核完成、审核未完成和策略阻断。
- **FR-034**: 报告必须记录所审核的版本、所选变更、配置版本和可得的工具版本，使同一次审核的结论可以被复核。
- **FR-035**: 报告必须把最高风险的变更放在工程师应优先查看的位置，并把已有可靠证据的检查标为不必反复人工确认。
- **FR-036**: 建议策略下，发现只进入报告，不自动阻止合并。只有已配置阻断规则所认定的确定性失败，才能产生策略阻断。
- **FR-037**: 仅来自辅助审查、没有确定性证据支撑的假设，默认不得阻止合并。严格策略下，被跳过、不可用或未完成的必需检查不得算作成功。
- **FR-038**: 在用真实历史变更完成误报与漏报对照之前，系统不得启用会阻止合并的质量门禁。
- **FR-039**: 一次审核不得修改业务源文件、需求工件、版本索引或提交历史，不得自动提交、合并、发布或部署，也不得访问生产数据或生产控制能力。
- **FR-040**: 报告必须写到已配置的报告位置，且不得覆盖源文件。报告位置不合法或试图逃出允许范围时，系统必须拒绝写入。
- **FR-041**: 构建可能生成文件或执行项目自带脚本时，系统必须说明这一风险，并支持对不可信仓库在隔离工作区中执行。构建命令只能来自受信任的配置，不能来自辅助审查临时生成的任意命令。
- **FR-042**: 未配置内部审查服务时，系统不得联系外部模型服务。已配置的服务不可用时，不得改送到其他服务。
- **FR-043**: 启用辅助审查时，系统只发送该审核任务所需的上下文；准备送审的内容中发现疑似密钥时，必须按策略遮盖或排除，并报告遮盖事实而不暴露密钥。
- **FR-044**: 报告不得包含环境密钥、访问令牌或不必要的源码摘录。源码、注释、文档和测试数据中针对审核者的指示不得改写审核策略。
- **FR-045**: 辅助审查的结论在获得可核验证据支持之前，必须标为待复核假设。审查服务返回无法使用的结果时，受影响的审查标为错误，其他成功检查必须保留。
- **FR-046**: 工程师必须能用明确的审核命令发起审核，并在配置有效时得到所请求的报告。配置无效时，系统必须在执行检查前停止并指出无效设置。
- **FR-047**: 工程师必须能查看用法说明和产品版本，且此时不启动审核。
- **FR-048**: 系统必须让调用方能够区分审核完成、审核未完成和策略阻断，以便以后接入持续集成或编程助手的包装层；v0.1 不要求本身提供网页管理台，也不要求绑定某一个编程助手或模型。

### Key Entities

- **审核对象**: 一次被审核的代码变更。包含版本库身份、基线版本、目标版本，以及是否包含未提交改动。
- **需求变更**: 所选 OpenSpec 变更中的提案、设计、任务、增量需求和相关长期规范。每条需求有标识、变更语义（新增、修改或删除）、场景和来源位置。
- **任务项**: 变更任务清单中的一项。具有完成标记，以及是否找到代码或测试支撑。
- **证据**: 支撑某条结论的需求位置、文件与行范围、测试结果或检查结果。分为直接证据、推断关联和证据不足。
- **检查结果**: 一次确定性检查的结果。包含命令、耗时、结束状态，以及通过、失败、跳过、错误或超时。
- **审核发现**: 一条归一后的问题或关注点。包含标识、类别、严重程度、摘要、证据状态、来源，以及是否为待复核假设。
- **变更质量报告**: 一次审核的可读报告和结构化报告。包含人工审核提示、需求覆盖、任务完整性、潜在风险、证据定位、检查结果、限制说明和执行信息。
- **审核策略**: 决定发现只作为建议，还是某类确定性失败构成策略阻断。默认是建议，不代替工程师的合并决定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对一个受支持的变更，工程师完成一次审核后，报告同时回答需求符合性、任务完整性、代码风险、测试有效性和审核效率。抽查时，100% 的结论要么附有可核查的证据，要么明确标为证据不足。
- **SC-002**: 在准备好的评估变更中，每条缺少实现证据的需求、每条标成完成但没有代码或测试支撑的任务，都被标成缺口；仅因缺少证据而被写成“代码一定有错”的条目为 0。
- **SC-003**: 工程师不打开全部变更文件，就能从报告摘要确定应最先查看的最高风险项；已有可靠检查证据的项被标成不必反复人工确认。
- **SC-004**: 一次结束的审核中，每项已配置检查都标为通过、失败、跳过、错误或超时之一。只要有必需检查未完成，报告就不得呈现为干净通过。
- **SC-005**: 一次审核结束后，业务源文件、需求工件和版本历史与审核前一致。报告只出现在指定的报告位置。
- **SC-006**: 不启用辅助审查时，已配置的确定性检查仍然完成，辅助审查维度全部标为未执行。
- **SC-007**: 启用辅助审查时，材料只发往明确配置的内部服务。该服务不可用时，改送到其他服务的次数为 0。报告和送审内容不包含已识别的密钥原文。
- **SC-008**: 在一组真实历史变更上，团队能够逐条记录自动结果与人工审核之间的真实问题、误报和遗漏。这次对照完成之前，阻止合并的质量门禁保持关闭。
- **SC-009**: 审核结束后，是否接受变更仍由工程师决定。产品自动批准合并的次数为 0。

## Assumptions

- v0.1 的审核对象是已经用 OpenSpec 管理需求与变更、并用版本库管理代码的 Java 服务端项目，以 Spring Boot 类项目为代表。项目继续使用它现有的构建和测试方式；SpecGuard 不替换这些工具，也不在本规格中规定 SpecGuard 自身的实现技术。
- 多模块项目会被识别并按配置的范围纳入审核。无法识别的布局会说明限制，而不是假装已经覆盖。
- “任务已完成”指所选变更的任务清单中该项已被标记完成。没有标记规则时，不猜测完成状态。
- 文件名或目录重叠只作为推断线索，不能单独充当需求已实现的直接证据。
- 可读报告供工程师本地阅读或附在拉取请求中；结构化报告供后续工具读取，并与可读报告保持同一套结论、证据和限制说明。v0.1 不自动把报告发布到拉取请求，也不提供网页管理台。
- 默认审核策略是建议模式。只有受信任配置中明确指定的确定性失败才可以产生阻断。辅助审查假设默认不阻断。
- 未使用真实历史变更完成误报、漏报和审核时间对照之前，不启用阻止合并的质量门禁。
- 辅助审查是可选项。内部审查服务的地址和模型由使用团队明确配置；示例地址不是可用终点。
- 构建和测试命令来自受信任配置。这些命令可能产生构建产物或执行项目自带脚本；不可信仓库应在隔离工作区中执行。
- 外部网络访问默认关闭。密钥遮盖采用保守策略：疑似密钥被排除或遮盖，并留下“已遮盖”的记录。
- 本产品不保证不存在逻辑缺陷、安全漏洞或回归，不代替 OpenSpec，也不代替现有测试、静态分析或代码扫描。
- 项目宪章仍是未填写的模板，本规格不依赖尚未确认的治理原则。
