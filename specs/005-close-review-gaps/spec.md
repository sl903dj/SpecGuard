# Feature Specification: 补齐质量门的证据与对照能力

**Feature Branch**: `005-close-review-gaps`

**Created**: 2026-10-27

**Status**: Draft

**Input**: User description: "本项目还缺少什么必备的功能？还有什么功能需要扩展？"

## User Scenarios & Testing *(mandatory)*

现有质量门已经能审核一份进行中的 OpenSpec 变更、一份 Spec Kit 功能，或一份从零建立的当前规范，并给出带证据的报告。工程师仍然自己决定是否接受变更。

对照产品要回答的五个问题，还缺三件必备能力，另有三类已有能力需要扩展：

- 必备：需求证据今天几乎只认“文件里出现了需求标识”，验收场景有没有被验证说不清楚。
- 必备：审核进行中的变更时，不能对照仓库里已经接受的当前规范，未声明的冲突会被漏掉。
- 必备：宪章要求用真实历史变更做误报和漏报对照之后，才可以考虑阻止合并的门禁。产品还不能记录和展示这次对照。
- 扩展：代码风险对边界、异常、空值、事务、并发、授权和兼容性的覆盖不稳定，许多结论没有位置或失败路径。
- 扩展：审核当前规范时，证据默认只来自选定版本范围；工程师不能明确改成“看目标版本的完整内容”。
- 扩展：多模块变更时，报告列出了模块，但没有说明已配置的构建和测试有没有覆盖到变更涉及的模块。

本功能不把质量门改成编程助手，也不扩大到 Java 服务端以外的项目。

### User Story 1 - 按验收场景判断需求证据 (Priority: P1)

工程师阅读报告时，需要知道每条需求是找到了直接证据、只有推断关联，还是证据不足。文件名刚好重叠不能写成需求已经实现。变更文件里出现需求标识，只说明有关联，不能写成验收场景已经通过。

每条验收场景要么能指到本次证据范围内、确实检查了该场景预期结果的测试，要么标成覆盖缺口。测试命令整体通过，不能把没有对上的场景写成已满足。找不到证据不是确定的实现错误。

**Why this priority**: 需求符合性和测试有效性是质量门要回答的核心问题。现在的证据规则回答不了“场景有没有被验证”。

**Independent Test**: 准备一组需求，分别带有标识出现在代码中、只有文件名重叠、有能对上预期结果的测试、只有恒真断言、以及完全没有线索。报告按各自情况标注；仅因文件名重叠或测试命令通过而被写成“已实现”的条目为 0。

**Acceptance Scenarios**:

1. **Given** 一条需求的标识出现在本次证据范围内的文件中，**When** 报告生成，**Then** 该需求标为直接证据，并说明这只代表找到关联，不代表验收场景已经通过。
2. **Given** 一条需求只能靠文件名或路径与变更文件重叠，**When** 报告生成，**Then** 该需求标为推断关联，并写明这不能单独证明需求已经实现。
3. **Given** 一条需求在证据范围内没有任何关联线索，**When** 报告生成，**Then** 该需求标为证据不足，且不被写成确定的实现错误，也不被写成已经通过。
4. **Given** 某条验收场景在证据范围内有测试检查了该场景写出的预期结果，且该检查不是恒定结果的空断言，**When** 报告生成，**Then** 该场景标为已有测试支撑，并给出测试位置。
5. **Given** 某条验收场景没有这样的测试，或相关测试只断言恒定结果，**When** 报告生成，**Then** 该场景标为覆盖缺口，不因测试命令整体通过而写成已满足。
6. **Given** 一条需求没有写出验收场景，**When** 报告生成，**Then** 报告说明该需求的场景审核不可用，不宣称场景已经通过。
7. **Given** 辅助审查声称某个场景已被覆盖，但证据范围内没有对应测试，**When** 报告生成，**Then** 该声称保持为待复核假设，不能把场景改成已有测试支撑。

### User Story 2 - 对照已接受的当前规范 (Priority: P1)

仓库里已经有一份接受过的当前规范，工程师又在审核一份进行中的变更。报告需要指出：变更是否在没有声明的情况下，否定了当前规范里仍然有效的要求或场景。已经明确写成新增、修改或删除的内容，不能仅仅因为“它是增量”就被当成冲突。

当前规范里的其他需求不能被算进这次变更自己的需求清单。没有当前规范时，这项审核不可用，不能写成已经通过。审核 Spec Kit 功能时，不能声称已经做过 OpenSpec 当前规范对照。

**Why this priority**: 选了变更就看不到整份已接受规范，未声明的需求冲突会直接进入人工审核的盲区。

**Independent Test**: 准备同时含有当前规范和一份变更的样例。其中放入一处未声明的冲突、一处已声明的修改，以及若干只存在于当前规范中的需求。报告只指出未声明冲突；当前规范独有的需求不出现在变更需求清单里。

**Acceptance Scenarios**:

1. **Given** 工程师选定一份进行中的变更，且仓库存在已接受的当前规范，**When** 审核进行，**Then** 报告把当前规范仅作对照上下文，不把它的需求并入该变更的需求清单。
2. **Given** 变更否定了当前规范中仍然有效的要求或场景，且没有把对应需求声明为修改或删除，**When** 报告生成，**Then** 报告指出这一未声明冲突，并给出两边的来源位置。
3. **Given** 变更已经把对应需求声明为新增、修改或删除，**When** 报告生成，**Then** 这一声明本身不被当成冲突。
4. **Given** 两边文字是否冲突无法判断，**When** 报告生成，**Then** 该项标为需要人工审核，不编造冲突，也不写成已经一致。
5. **Given** 工程师选定的是变更，但仓库没有当前规范，**When** 报告生成，**Then** 报告说明规范对照不可用，不宣称与当前规范一致。
6. **Given** 工程师选定的是当前规范或 Spec Kit 功能，**When** 审核进行，**Then** 系统不擅自另选一份变更来做对照，也不宣称已完成 OpenSpec 当前规范对照。

### User Story 3 - 记录历史误报与漏报 (Priority: P1)

技术负责人需要用真实历史变更核对：工具指出的问题里哪些成立、哪些是误报，以及人工发现但工具没指出的漏报。对照没有完成时，报告必须写明，并且默认结果仍然不阻止合并。工程师明确把对照标成完成，也不能自动改成阻止合并，更不能自动接受变更。

对照记录由工程师保存在已配置的报告位置。系统只读取它。记录缺失、读不了，或没有至少一次完整的历史变更对照时，对照状态都是未完成。把“已完成”写在一份没有任何结论的记录上，必须被拒绝，状态仍为未完成。

**Why this priority**: 没有这份对照，阻止合并的门禁就没有依据。宪章禁止在对照完成前把未知说成可以阻断。

**Independent Test**: 分别使用“没有记录”“记录不完整”“有一次完整历史对照并被工程师标成完成”三种情况审核。前两种报告写明未完成且默认不阻断；第三种写明已完成，但默认仍然不阻断，自动接受变更的次数为 0。

**Acceptance Scenarios**:

1. **Given** 报告位置没有对照记录，**When** 审核结束，**Then** 报告写明历史对照未完成，默认结果不阻止合并。
2. **Given** 某次历史变更上，工具发现没有逐条标成真实问题或误报，或者没有说明漏报（含明确的“无漏报”），**When** 读取记录，**Then** 该次历史变更不算完成对照。
3. **Given** 记录把对照标成已完成，但没有任何一次完整的历史变更对照，**When** 审核开始前的记录校验，**Then** 系统拒绝这一完成标记，报告仍写明对照未完成。
4. **Given** 至少有一次历史变更已完整对照，且工程师明确把整体对照标成完成，**When** 报告生成，**Then** 报告写明对照已完成，并给出已对照的变更数量；默认结果仍然不阻止合并。
5. **Given** 对照已经完成，**When** 审核结束，**Then** 仅来自辅助审查的假设仍然不能单独阻止合并，系统自动接受变更的次数为 0。
6. **Given** 对照记录里含有疑似密钥，或结论指向不存在的发现，**When** 报告生成，**Then** 报告不写出密钥原文，并说明哪些结论无法对应到发现；不因此把对照写成已完成。

### User Story 4 - 补齐已承诺的代码风险 (Priority: P2)

高级工程师需要报告覆盖变更里看得到的边界条件、异常处理、空值与空输入、事务边界、并发、授权、公开接口兼容、已保存数据，以及依赖或配置变化。每一类要么给出位置和一条说得通的失败路径，并标明证据是已证实、待复核假设还是证据不足；要么明确写这一类缺少判断所需的上下文。没有失败路径的内容不能写成缺陷。检查没有发现，不能写成代码安全。

**Why this priority**: 风险排序已经存在，但覆盖不稳定，工程师无法信任“没写出来”是真的没有，还是根本没查。

**Independent Test**: 准备一组变更，分别包含上述每一类风险，以及一类缺少上下文的情况。报告对每一类给出“有位置和失败路径的发现”或“上下文不足”之一；写成“代码安全”的条目为 0。

**Acceptance Scenarios**:

1. **Given** 变更中某一类风险能定位到具体位置，并说得通一条失败路径，**When** 报告生成，**Then** 发现包含位置、失败路径和证据状态。
2. **Given** 只有确定性检查支持该风险，**When** 报告生成，**Then** 证据状态为已证实；否则为待复核假设或证据不足。
3. **Given** 判断该风险所需的代码、配置或领域规则不在本次证据范围内，**When** 报告生成，**Then** 报告写明这一类上下文不足，不编造位置或失败路径。
4. **Given** 本次没有形成任何风险发现，**When** 工程师阅读摘要，**Then** 报告写明实际检查了哪些风险类别，并且不宣称代码安全或没有缺陷。

### User Story 5 - 明确当前规范的证据范围 (Priority: P2)

审核当前规范时，证据默认仍只来自工程师选定的版本范围。范围外的文件不是证据。工程师可以另外明确选择：把目标版本当时的完整内容作为证据范围。报告必须写明这次用的是哪一种。这个选择只适用于当前规范。用在进行中的变更或 Spec Kit 功能上时，系统在任何检查开始前拒绝。

**Why this priority**: 从零建立规范的团队，有时需要看目标版本里已经存在的全部内容，而不是只看一小段差异。这个选择必须显式，避免把今天的版本范围规则悄悄改掉。

**Independent Test**: 对同一份当前规范分别做两次审核：不额外选择时，只有版本范围内的文件能成为证据；明确选择完整内容后，报告写明范围是目标版本的完整内容，且版本范围外、又不在该目标版本中的文件仍然不是证据。对变更使用该选择时，检查开始前被拒绝。

**Acceptance Scenarios**:

1. **Given** 工程师审核当前规范且没有改证据范围，**When** 报告生成，**Then** 只有选定版本范围内的文件能作为证据，报告写明使用的是版本范围。
2. **Given** 工程师明确选择用目标版本的完整内容审核当前规范，**When** 报告生成，**Then** 报告写明证据范围是该目标版本的完整内容，并只使用其中的文件。
3. **Given** 工程师把“完整内容”用在进行中的变更或 Spec Kit 功能上，**When** 审核开始，**Then** 系统在任何检查开始前拒绝，并说明该选择只适用于当前规范。
4. **Given** 使用任一证据范围完成审核，**When** 比较审核前后的仓库，**Then** 规范工件、业务源文件、版本索引和提交历史保持不变。

### User Story 6 - 说明构建和测试覆盖了哪些模块 (Priority: P3)

变更涉及多个构建模块时，工程师需要知道已配置的构建和测试是针对整个仓库跑的，还是没有覆盖到某个涉及的模块。未执行的检查不能写成通过。系统不猜测、也不临时编造构建命令。项目布局无法识别时，报告说明这个限制。

**Why this priority**: 这是已有项目识别能力的诚实性扩展。它帮助工程师决定要不要亲自补跑，但不改变需求证据和对照记录的价值。

**Independent Test**: 准备一个变更触及两个模块、但构建和测试只按整个仓库配置了一次的样例。报告列出涉及的模块，并说明这次命令没有按模块分别执行。再准备一个无法识别布局的样例，报告说明限制，且不把未执行写成通过。

**Acceptance Scenarios**:

1. **Given** 变更涉及多个构建模块，且已配置的构建或测试是一次仓库级命令，**When** 报告生成，**Then** 报告列出涉及的模块，并说明该命令没有分别覆盖每个模块。
2. **Given** 某个涉及的模块没有被已配置的检查执行到，**When** 报告生成，**Then** 该项标为未执行或不可用，绝不标为通过。
3. **Given** 项目布局无法可靠识别，**When** 审核继续，**Then** 报告说明无法判断模块覆盖，并且不编造构建命令。

### Edge Cases

- 证据范围内没有任何代码或测试。全部需求和场景标为证据不足或覆盖缺口，审核仍可完成，并说明范围内没有可核验证据。
- 需求标识重复、正文为空或工件无法读取。系统在检查开始前停止，本功能不放宽这一规则。
- 当前规范由多组能力组成。对照时保留能力名称和来源位置，不把不同能力的同名要求悄悄合并。
- 变更删除了需求。删除声明本身不是冲突；当前规范里若仍把该要求写成有效，且变更没有相应删除声明，才是未声明冲突。
- 对照记录不是可读文本、结论种类无法识别，或同一条发现有互相矛盾的结论。系统说明记录不可用，对照状态保持未完成，已经完成的其他检查保留。
- 工程师选择纳入未提交改动。证据范围规则与原来一致：只有明确纳入时，未提交内容才进入证据；对照记录的读取不改变这一规则。
- 辅助审查服务不可用。受影响的辅助审查标为错误，需求证据、规范对照和已完成的确定性检查保留。
- 严格策略下，已配置且已证实的确定性失败仍可按工程师的明确选择产生阻断信号。历史对照未完成时，报告必须同时写明门禁依据不足，且辅助审查假设不能单独造成阻断。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 对所选审核对象中的每条需求，系统必须给出且只给出一种主证据状态：直接证据、推断关联或证据不足，并说明理由。
- **FR-002**: 仅有文件名或路径重叠时，系统必须标为推断关联，不得写成需求已经实现。
- **FR-003**: 需求标识出现在证据范围内的文件中时，系统必须标为直接证据，并说明这不代表验收场景已经通过，也不代表可以接受该变更。
- **FR-004**: 验收场景只有在证据范围内的测试检查了该场景写出的预期结果，且该检查不是恒定结果的空断言时，才可以标为已有测试支撑。
- **FR-005**: 没有满足 FR-004 的验收场景必须标为覆盖缺口。测试命令整体通过不得把该场景写成已满足。覆盖缺口不是确定的实现错误。
- **FR-006**: 需求没有验收场景时，系统必须说明场景审核不可用，不得宣称场景已经通过。
- **FR-007**: 测试命令失败必须与测试未能执行区分开。任一情况都不得推断所有需求已经满足。
- **FR-008**: 辅助审查关于场景已被覆盖的输出，在没有 FR-004 所述测试时，必须保持为待复核假设。
- **FR-009**: 所选对象是进行中的 OpenSpec 变更且存在已接受的当前规范时，系统必须把当前规范作为对照上下文，并报告未声明冲突。
- **FR-010**: 未声明冲突指变更否定了当前规范中仍然有效的要求或场景，且没有把对应需求声明为修改或删除。报告必须给出两边的来源位置。
- **FR-011**: 已声明的新增、修改或删除本身不得被当成冲突。无法判断是否冲突时，必须标为需要人工审核，不得编造冲突或写成已经一致。
- **FR-012**: 当前规范中的需求不得并入该变更自己的需求清单，也不得改写变更原有的新增、修改、删除语义。
- **FR-013**: 所选对象是变更但没有当前规范时，系统必须说明规范对照不可用，不得宣称已经一致。所选对象是当前规范或 Spec Kit 功能时，不得擅自另选变更做对照，也不得宣称已完成 OpenSpec 当前规范对照。
- **FR-014**: 系统必须读取工程师保存在已配置报告位置的历史对照记录。记录不存在、无法读取或结论无法识别时，历史对照必须标为未完成，其他已成功的检查必须保留。
- **FR-015**: 一次历史变更只有在每条工具发现都被标为真实问题或误报，并且漏报已被记录（包括明确的“无漏报”）时，才算完成对照。同一发现的矛盾结论使该次对照无效。
- **FR-016**: 整体对照只有在至少一次历史变更已完成对照，且工程师明确标成完成时，才可以在报告中写成已完成。没有完整历史变更却标成完成时，系统必须拒绝该标记并保持未完成。
- **FR-017**: 历史对照未完成或已完成，默认审核结果都不得阻止合并。对照完成不得自动改变默认策略，也不得使系统接受、拒绝或合并变更。
- **FR-018**: 仅来自辅助审查的假设不得因对照记录而变成阻断理由。工程师若另行明确选择只让已证实的确定性失败产生阻断信号，报告仍必须同时写明历史对照是否完成。
- **FR-019**: 对照记录不得被写入需求工件、业务源文件或版本历史。记录中的疑似密钥不得出现在报告中。无法对应到发现的结论必须被说明，并且不能用来把对照写成已完成。
- **FR-020**: 对边界条件、异常处理、空值与空输入、事务边界、并发、授权、公开接口兼容、已保存数据、依赖或配置变化，系统必须要么给出带位置、说得通的失败路径和证据状态的发现，要么写明该类别缺少上下文。
- **FR-021**: 风险发现只有在确定性检查支持时才可以标为已证实；否则必须标为待复核假设或证据不足。没有失败路径时不得写成缺陷。没有任何风险发现时，必须写明实际检查过的类别，不得宣称代码安全或没有缺陷。
- **FR-022**: 审核当前规范时，证据范围默认是工程师选定的版本范围。未明确改范围时，范围外文件不得作为证据，报告必须写明使用的是版本范围。
- **FR-023**: 工程师可以明确选择把目标版本的完整内容作为当前规范的证据范围。报告必须写明这一范围，且只使用该目标版本中的文件。
- **FR-024**: 把完整内容证据范围用于进行中的变更或 Spec Kit 功能时，系统必须在任何检查开始前拒绝。
- **FR-025**: 变更涉及多个构建模块时，报告必须列出这些模块，并说明已配置的构建和测试是仓库级一次执行，还是没有覆盖到某个涉及模块。未执行的检查不得标为通过。布局无法识别时必须说明限制，不得编造命令。
- **FR-026**: 不使用本功能新增选择时，已有的变更审核、当前规范审核和 Spec Kit 审核必须保持可用，原有的未选择即停止、只读和报告位置限制保持有效。
- **FR-027**: 一次审核不得修改业务源文件、需求工件、版本索引或提交历史，不得自动提交、合并、发布或部署。报告只写到已配置的报告位置。
- **FR-028**: 人类可读报告和结构化报告必须包含同一套需求证据、场景覆盖、规范对照、历史对照状态、风险类别和证据范围结论。最高风险项仍排在应优先查看的位置。

### Key Entities

- **需求证据**: 一条需求在本次证据范围内的主状态，取直接证据、推断关联或证据不足之一，并带有理由。
- **验收场景**: 需求中写出的一组可观察条件和预期结果。它要么有测试支撑，要么是覆盖缺口，要么因需求未写场景而不可用。
- **已接受的当前规范**: 仓库中已经接受、用来描述系统要求的整份规范。它是对照上下文，不是本次变更的需求清单。
- **未声明冲突**: 变更否定了当前规范里仍然有效的要求或场景，但没有把对应需求声明为修改或删除。
- **历史对照记录**: 工程师保存在报告位置的对照结论。每条工具发现可标为真实问题或误报，并单独记录漏报。
- **风险发现**: 某一风险类别上的关注点，包含位置、失败路径和证据状态；缺少上下文时用限制说明代替发现。
- **证据范围**: 本次允许用来支撑结论的内容边界。默认是选定版本范围；只有当前规范可以明确改成目标版本的完整内容。
- **构建模块**: 变更触及的、可识别的构建单元。报告用它说明检查覆盖，不把它当作需求已经实现的证据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在准备好的样例中，100% 的需求都有且只有一种主证据状态。仅因文件名或路径重叠而被写成“已经实现”的需求为 0。
- **SC-002**: 100% 的已写出验收场景要么指到证据范围内的有效测试，要么标为覆盖缺口。仅因测试命令整体通过而被写成“已满足”的场景为 0。没有场景的需求中，被写成“场景已通过”的数量为 0。
- **SC-003**: 在同时含有当前规范和变更的样例中，种入的未声明冲突 100% 被报告并带有两边来源。仅因“属于增量”而被当成冲突的已声明修改为 0。被并进变更需求清单的当前规范独有需求为 0。
- **SC-004**: 没有完整历史对照时，100% 的报告写明对照未完成，且默认结果不阻止合并。对照被接受为完成后，报告写明已完成变更的数量；自动接受变更的次数仍为 0，仅由辅助审查假设造成的阻断次数为 0。
- **SC-005**: 在覆盖全部风险类别的样例中，每一类都要么有位置、失败路径和证据状态，要么写明上下文不足。宣称“代码安全”或“没有缺陷”的条目为 0。
- **SC-006**: 不改证据范围时，当前规范审核与今天一样只使用选定版本范围。明确改成完整内容后，报告写明新范围；对该选择的误用在检查开始前被拒绝的比例为 100%。
- **SC-007**: 工程师只读一次审核摘要，就能指出最弱的需求证据、是否存在未声明冲突、历史对照是否完成，以及应先看的最高风险。多模块样例中，未被单独覆盖的涉及模块 100% 被点名。
- **SC-008**: 一次审核结束后，业务源文件、需求工件、版本索引和提交历史与审核前一致。报告只出现在已配置的报告位置。

## Assumptions

- 本功能的使用者是已经用 SpecGuard 审核 Java 服务端仓库的工程师。仓库用 OpenSpec、Spec Kit，或两者之一管理需求，并用版本库管理代码。
- 审核对象仍是 Java 服务端变更或与之对应的需求工件。扩展到其他技术栈需要先修订项目宪章，不属于本功能。
- 不使用新增选择时，版本范围证据、变更与当前规范二选一、以及 Spec Kit 的对象选择规则保持不变。
- “恒定结果的空断言”指测试没有检查场景写出的预期结果，只复述一个固定答案。
- 历史对照记录由工程师维护并放在已配置的报告位置。系统读取它，不代替工程师做真实问题、误报或漏报的裁决。
- 至少一次历史变更完成逐条结论后，工程师才可以明确把整体对照标成完成。完成只改变报告中的对照状态，不改变默认的建议式结果。
- 默认审核结果仍然是建议。是否接受变更由工程师决定。本功能不提供网页管理台，也不自动把报告发到拉取请求。
- 本功能不生成或修改业务代码，不编造当前规范的任务清单，也不把辅助审查变成确定性证据。
- 本功能不替换项目已有的构建、测试或静态检查，只如实说明它们覆盖了什么、没覆盖什么。
