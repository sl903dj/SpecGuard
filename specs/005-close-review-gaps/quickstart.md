# Quickstart: 补齐质量门的证据与对照能力

验证六条用户路径。字段和拒绝条件以 [review-inputs.md](contracts/review-inputs.md) 与 [report.md](contracts/report.md) 为准。实现阶段用 pytest 执行，本计划不把尚未运行的测试写成已经通过。

## 准备

- Python 3.11+ 和仓库内的测试环境。
- 一个临时 Git 仓库，同时放有 OpenSpec 当前规范和一份进行中的变更。
- 版本范围内放入：含需求标识的实现文件、只在文件名上重叠的文件、检查了场景预期的测试、只有恒真断言的测试。
- 范围外保留另一个已存在文件。
- 报告目录中分别准备缺失、不完整、虚假完成和一次完整历史审核四份对照记录。不要把真实密钥写入样例；秘密样例使用明显的测试占位值。

## 场景 1: 需求证据与验收场景

对上述仓库按默认版本范围审核该变更。

预期：

- 含标识的需求为直接证据，说明不代表场景已经通过。
- 只有文件名重叠的需求为推断关联，不被写成已经实现。
- 没有线索的需求为证据不足，不是确定缺陷。
- 检查了预期结果的场景为已有测试支撑并带有测试位置。
- 恒真断言或没有对上预期的场景为覆盖缺口。测试命令通过不改变该结果。
- 没有场景的需求写明场景审核不可用。

## 场景 2: 当前规范对照

在变更中放入一处未声明的对立场景、一处已声明修改，并在当前规范中保留一条变更未提及的需求。

预期：

- 只报告未声明冲突，两边都有来源位置。
- 已声明修改不因自己是增量而成为冲突。
- 当前规范独有需求不出现在变更需求清单。
- 去掉当前规范后，报告写明规范对照不可用。
- 改为审核当前规范或 Spec Kit 功能时，不另选变更，并写明未做这项对照。

## 场景 3: 历史对照

用四份记录各审核一次。

预期：

- 缺失和不完整记录都写明对照未完成，默认结果不阻止合并。
- 没有完整历史审核却声明完成时，完成标记被拒绝，状态仍为未完成，审核仍写出报告。
- 一次完整历史审核且声明完成时，报告给出数量 `1`，默认结果仍不阻止合并。
- 辅助审查假设不因记录而变成阻断。测试占位密钥不出现在报告中。

## 场景 4: 风险类别

准备一组差异，分别命中空 catch、空的空值判断和集合长度上界，并另备一组没有任何这些线索的差异。

预期：

- 三次命中都有真实行号、失败路径和已证实状态。
- 九类风险每次都出现。没有线索的类别写明缺少上下文，不使用编造行号。
- 没有任何风险发现时，摘要仍列出已检查的类别，且不宣称代码安全。

## 场景 5: 证据范围

对同一份当前规范审核两次：默认范围，以及 `--evidence-scope target-tree`。再把后者用于一份变更。

预期：

- 默认报告的证据范围是版本范围，范围外文件不是证据。
- 完整内容报告写明目标版本树，并只引用该树中的文件。
- 用于变更时退出 `4`，标准错误说明该选择只适用于当前规范，且没有新报告。
- 两次成功审核前后，规范、业务源文件和版本历史不变。

## 场景 6: 模块覆盖与旧路径

准备一个变更触及两个构建模块、构建命令按整个仓库配置一次的仓库，以及一个无法识别布局的仓库。再跑现有 OpenSpec 变更、当前规范和 Spec Kit 回归。

预期：

- 两个模块都被点名，并说明仓库级命令没有分别执行。对应检查不是通过，且没有新编的命令。
- 无法识别布局时只说明限制。
- 不使用新选择时，旧审核对象、未选择即停止和只读限制保持可用。

## 验证命令

实现完成后在检出根目录运行：

```bash
.venv/bin/python -m pytest -q
```

场景分别落到 `tests/unit/test_evidence_scope.py`、`tests/unit/test_scenario_assessment.py`、`tests/unit/test_consistency.py`、`tests/unit/test_calibration.py`、`tests/unit/test_risk_classes.py`、`tests/unit/test_module_coverage.py`，以及 `tests/integration/test_us1_evidence.py`、`test_us2_consistency.py`、`test_us3_calibration.py`、`test_us4_risk.py`、`test_us5_evidence_scope.py`、`test_us6_modules.py`。现有 OpenSpec 与 Spec Kit 测试必须继续通过。
